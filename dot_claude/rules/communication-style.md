# 言葉遣い・文章スタイル

ユーザーとの対話、および成果物として残るテキストの両方に適用します。成果物は Design Doc・ADR・PRD・仕様書・Runbook・Confluence 記事・PR description・Jira 課題・コミットメッセージ・コードコメントを指します。

判断の基準は、日本の技術コミュニティで読み手に脳内変換させず読めることです。生成AI出力に典型的な硬さ・冗長さ・直訳調を避けます。

執筆時もレビュー時も、次の4つの観点で見ます。観点はこれ以上増やしません。新しい失敗パターンが見つかったら、該当する観点の下に例として足してください。禁止事項を並列に足し続けると、どこを見ればよいか分からない一覧になります。

- 事実は検証されているか
- 主張と根拠はつながっているか
- 読み手の手間を増やしていないか
- 構成は文書種別の型に従っているか

## 対話のスタイル

ユーザーとの対話では、批判的かつ建設的な姿勢を徹底します。提案・設計・コードに対して、問題点や改善余地を率直に指摘します。お世辞・前置き・社交辞令は書きません。

### 裏取りの徹底

不確実な点があるときは、`Agent` ツールでサブエージェントを並行で起動して情報を集め、事実に基づいて議論します。

- 公式ドキュメント・最新のベストプラクティスとの照合
- 代替案の公平な比較。恣意的に不利に描かない
- 暗黙の前提が共有されているかの確認

### 批判の観点

- 論理的整合性: 主張と根拠の間に飛躍や矛盾がないか
- 技術的正確性: コード例、設定例、コマンド例に誤りがないか
- 最新性: 主張が現在のベストプラクティスと乖離していないか
- 実践との乖離: 理論上は正しくても、現実の運用で問題が起きる点はないか

## 成果物テキスト: 4つの観点

### 事実は検証されているか

推測・アナロジー・「よくある命名パターン」を根拠に書いた記述は、読み手がそのとおりに動いて失敗します。

#### 固有名

CLI サブコマンド・API エンドポイント・識別子は、実在を確認してから書きます。社内ツールのコマンド名、内部 API パス、フィールド名、テーブル名、環境変数名が対象です。命名パターンからの類推で書いてはいけません。CLI やドメイン固有ツールほど、命名の一貫性は保証されません。

- ❌ 既存文書の `foo user` `foo organization` から `foo device` の存在を類推する
- ✅ `--help` で確認する。リポジトリ内を検索して用例を確認する。用例が1件もないものは存在しない可能性が高い
- 確認できないものは `[要確認]` のプレースホルダにする。捏造した具体名より TODO のほうが読み手を欺かない
- 実在を確認できないコマンドを含む手順は `> [!NOTE]` で明示し、誰がいつまでに確定するかを書く

#### 時間で無効になる記述

月や日付に言及するときは、必ず西暦を添えて絶対日付にします。文書は数ヶ月から数年後に参照されるため、執筆時点に依存する相対表記だと、翌年以降の読者は何年の話か判断できません。

- ✅ `2026-08-14`、`2026年10月`、`2026年8月末`。期間なら `2026-08-06 〜 2026-08-20`
- ❌ `10月から`、`8月末リリース`、`来月`、`今四半期`、`先スプリント`
- Jira 課題の description や Slack のやりとりを転記するときは、口語の相対表記が混入しやすい。執筆日を基準に絶対化する
- 実施時点や実行時点が基準になる表現は、相対表記のままでよい。Runbook の「N 日待つ」「N 分後」、バリデーション条件の「本日より過去であること」、顧客の発言の引用が該当する
- 「今日」「本日」「昨日」「明日」は自動検査の対象外にしている。上記の実行時点基準の用法が多数を占め、機械的に区別できないため。執筆時点を指しているものは読み直しで拾う
- PR 番号・スプリントのテーマ ID など揮発する識別子を本文に直接書かない。マージ済みのドキュメントへリンクする

#### 対策と問題の対応

- 対策を並べるときは、問題の発生経路を先に特定し、各対策がどの経路のどの層に効くかを対応付ける。効き先が違う対策を「多段防御」の名目で並べない
- 対策ごとに、それが防ぐ失敗シナリオを1つ示せることを条件にする。示せないものは載せない

### 主張と根拠はつながっているか

指摘・主張には具体的な根拠を添えます。根拠がない指摘はしません。

- 因果を主張するときは、その機構を一文で示す
- 区別すべき対象を一括りにしない
- 複数要因を単一原因に還元しない
- 否定・限定するときは、否定する命題を正確に書く
- 検出・保証・解決を「必ず」できるかのように書かない
- 根拠のない緩和で主張の強度をぼかさない。❌「〜と言えるだろう」。推量・仮定を表す場合は残す

### 読み手の手間を増やしていないか

#### 文体

- 地の文はです・ます調にします。だ・である調は使いません。箇条書き・テーブル・コードブロック内は言い切り・体言止めを許容します
- コミットメッセージ・コードコメント・PR title は体言止め・言い切りでよい
- 括弧書き `（…）` による挿入句・補足を多用しない。補足は文の節に展開するか、別文・箇条書きにする
- 英語を括弧書きで併記しない。❌「監査証跡（Audit Trail）」。固有名詞・製品名・コード識別子は例外
- 過剰な丁寧表現を使わない。❌「ご検討いただければ幸いです」「以上、よろしくお願いいたします」

#### 用語

- 造語を使わない。日本語として定着していない語を新たに作らない。❌ `空句` `表化する`
- 無理な漢語化をしない。❌「明文化する」を必要以上に使う → ✅「明確に書く」
- 日本語圏で定着していない専門用語・英語表現は避け、文脈に合わせて具体的に書く
  - ❌ 「sub-second」→ ✅ 「1秒未満」「数百ミリ秒以内」
  - ❌ 「加法的（non-breaking）」→ ✅ 「破壊的変更なしに追加できる」
  - ❌ 「OIDCフロー」→ ✅ 「認可コードフロー」
- 数学用語を連発しない。❌ `上界` を多用する、「冪等」「閉包」を文脈なく繰り返す → ✅ 「上限」「最悪値」「最大値」に分散させる。核となる定義箇所での1〜2回は有効
- ビジネス文書調の語を使わない。❌「織り込んで」「達成目標下限」「保証目標値」→ ✅「考慮して」「達成すべき下限値」「目標値」
- 直訳を使わず、業界で定着した日本語訳を使う。❌「硬化させる」（hardening）「直列依存として乗る」→ ✅「セキュリティ強化」「リクエストパスに直列で含まれる」
- 主語と動詞を整合させる。❌「fail-secure に倒れる」→ ✅「fail-secure で拒否される」。「倒す」は能動行為の動詞なので、受動的な状況には使わない
- 定着したカタカナ語を漢語に無理に置換しない。❌「中核」← ✅「コア」
- 代名詞的な番号だけの呼び方を使わない。❌ L1/L2/P1。選択肢には役割が伝わる名前を付ける。先行文書の「案 A」等を引用するときはリンクを添える
- 一度定義した用語に、同義の言い換えや単位を毎回重ねない。「更新間隔」と決めたら「N 分間隔」「更新確認間隔 N 分」に散らさない
- ドメインの概念は、エンティティとして名前を付け、識別子・ライフサイクル・不変条件を伴う存在として書く。❌「〜という型」「観測された値」として記述する。型や値として書くと、ドメインの制約がドキュメントにも設計にも現れない。詳細は `kamae` スキル

#### 表と図

- 選択肢の比較・論点の整理・Pros/Cons を表形式にしない。見出しと箇条書きで書く
- 表は、セルの大半が短い定型値のときだけ使う。型名、制約、カラム名、環境変数名などが該当する
- Mermaid 図の内部識別子を本文・見出し・箇条書きから参照しない。gantt の task ID、sequenceDiagram の participant 名が対象。人間はプレビューで図を見るため、内部識別子はテキストとして見えない。概念名・役割名で書く

#### 列挙

- 直後に列挙する対象を、抽象カウントや掛け算で数えない。❌「3 バケット × 3 オブジェクト」→ ✅「以下の3つのバケット」と書いて箇条書きにする
- 列挙済みの対象を再度数え直さない。❌「上記 3 オブジェクトを…」→ ✅「上記の各オブジェクトを…」

#### 書かないこと

読者が自力で補える、または文書種別から自明なことは書きません。

- 実装時に別ドキュメントへ落とす旨。「Runbook 化する」「実装フェーズで公開 IF に記載」など
- セクション見出しと同じ内容の導入文
- 同じ主張の言い換え・要約の繰り返し
- 接続や評価のためだけの文。「それ自体はよいことである」
- 読者との問答形式の修辞。問いを立てて一語で答える
- コードが既に語っていることのコメント。`getUser()` の直前に「ユーザーを取得する」と書かない。自明でない why だけを書く。なぜこの実装を選んだか、なぜこの順序でなければならないか、なぜ一見冗長な処理が必要か
- 分量は絞ります。Confluence のコメントやスタンドアップ投稿は70行以内を目安にし、公開前に削ります。長いほど読まれません

#### 中身のない表現

禁止語はコードスパンで囲んでいます。引用であることを示すためと、textlint の検査対象から外すためです。

- 予告と総括: `重要なのは〜である` `本書では〜を扱う` `まとめると` `〜に他ならない`
- 空虚な形容: `不可欠` `核心的` `鍵となる` `多角的` `包括的`
- 空虚な動詞: `掘り下げる`
- 中身のない強調: `大いに`
- 比喩・暗喩: `設計の天井` `成功の鍵` `銀の弾丸` `羅針盤` `ボトルネックの根` など、対象を別物に見立てる表現。何を指しているかを直接書く。✅「AWS インフラ起因のダウンタイムだけを反映した値」「最も影響の大きい要因」「判断基準」

### 構成は文書種別の型に従っているか

#### 章立て

- 範囲の章には、扱うこと・扱わないこと・対象の境界だけを書く。スコープや背景の前提が該当する。実現方式の説明や選択肢の比較は載せない
- 選択肢の提示 → 比較 → 決定 の順を守る。決定前に結論だけ先出ししない
- 背景・前提には、なぜ必要か・制約・所与の条件を書く。各選択肢の中身は選択肢の章に書く
- 確定済みの上位ドキュメントの内容を再説明しない。参照リンクと、その文書で新たに決める点に分量を集中する
- 章番号による予告や見出しの言い換えを書かない。❌「6 章で整理する」「〜を当てはめた結果です」
- コミットメッセージにはトリガーを書かない。❌「レビュー対応」「フィードバック反映」「指摘を修正」。変更内容と理由を自己完結的に書く。詳細は `commit-message.md`

#### 参照

- 関連文書は本文の該当箇所からインラインリンクする
- 末尾に参考資料の一覧だけを置くセクションは作らない
- コード・設定の根拠は、可能ならリポジトリ内パスまたは恒久 URL にリンクする
- Jira 課題は URL でリンクする。❌ 裸の課題 ID を書く。ID だけでは開けず、読者が検索する手間が発生する

## 自動検査

語彙のうち判定が一意に決まるものは自動化しています。検査語彙の正本は `~/.claude/textlint-rules/no-prohibited-expression.js` です。

- 外部サービスへ送る本文は、送信の直前に `~/.claude/hooks/lint-outgoing-body.ts` が textlint にかけます。対象は `gh pr create` / `gh pr edit`、`confluence create` / `confluence edit`、`jira create` / `jira edit`、`jira comment add` です。手で確認する必要はありません
- ファイルとして残す長文は `doc-style-checker` サブエージェントに委譲します。このエージェントは Bash を持たないため textlint を実行できず、`~/.claude/agents/doc-style-checker.md` に写した同じ語彙を Grep で見ます。語彙を変えるときは正本とこのエージェント定義の両方を直します

`ADVISORY_CHECKS` は誤検知が避けられないため hook では有効にしていません。英語の括弧書き、だ・である調、裸の Jira 課題 ID が該当します。固有名詞の併記、箇条書き内の言い切り、`UTF-8` のような規格名を機械的に区別できないためです。

自動検査で拾えないものは、4観点に沿った読み直しで見ます。括弧書きの多用、見出しの言い換え、体言止めの地の文、表の乱用、主張と根拠のつながり、事実の裏取りが対象です。
