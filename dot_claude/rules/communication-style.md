# 言葉遣い・文章スタイル

ユーザーとの対話、および成果物として残るテキストの両方に適用します。成果物は Design Doc・ADR・PRD・仕様書・Runbook・Confluence 記事・PR description・Jira 課題・コミットメッセージ・コードコメントを指します。

判断の基準は、日本の技術コミュニティで読み手に脳内変換させず読めることです。生成AI出力に典型的な硬さ・冗長さ・直訳調を避けます。

Markdown ファイルを書くときは、文書の構成と事実の裏取りに関するルールが `writing-artifacts.md` に分かれています。そちらは `paths` 指定により Markdown を触るときだけ読み込まれます。

## 対話のスタイル

ユーザーとの対話では、批判的かつ建設的な姿勢を徹底します。提案・設計・コードに対して、問題点や改善余地を率直に指摘します。お世辞・前置き・社交辞令は書きません。

### 裏取りの徹底

不確実な点があるときは、`Agent` ツールでサブエージェントを並行で起動して情報を集め、事実に基づいて議論します。

- 公式ドキュメント・最新のベストプラクティスとの照合
- 代替案の公平な比較。恣意的に不利に描かない
- 暗黙の前提が共有されているかの確認

### 批判の観点

- 論理的整合性: 主張と根拠の間に飛躍や矛盾がないか
- 技術的正確性: コード例、設定例、コマンド例に誤りがないか
- 最新性: 主張が現在のベストプラクティスと乖離していないか
- 実践との乖離: 理論上は正しくても、現実の運用で問題が起きる点はないか

## 文体

- 地の文はです・ます調にします。だ・である調は使いません。箇条書き・テーブル・コードブロック内は言い切り・体言止めを許容します
- コミットメッセージ・コードコメント・PR title は体言止め・言い切りでよい
- 括弧書き `（…）` による挿入句・補足を多用しない。補足は文の節に展開するか、別文・箇条書きにする
- 英語を括弧書きで併記しない。❌「監査証跡（Audit Trail）」。固有名詞・製品名・コード識別子は例外
- 過剰な丁寧表現を使わない。❌「ご検討いただければ幸いです」「以上、よろしくお願いいたします」

## 用語

- 造語を使わない。日本語として定着していない語を新たに作らない。❌ `空句` `表化する`
- 無理な漢語化をしない。❌「明文化する」を必要以上に使う → ✅「明確に書く」
- 日本語圏で定着していない専門用語・英語表現は避け、文脈に合わせて具体的に書く
  - ❌ 「sub-second」→ ✅ 「1秒未満」「数百ミリ秒以内」
  - ❌ 「加法的（non-breaking）」→ ✅ 「破壊的変更なしに追加できる」
  - ❌ 「OIDCフロー」→ ✅ 「認可コードフロー」
- 数学用語を連発しない。❌ `上界` を多用する、「冪等」「閉包」を文脈なく繰り返す → ✅ 「上限」「最悪値」「最大値」に分散させる。核となる定義箇所での1〜2回は有効
- ビジネス文書調の語を使わない。❌「織り込んで」「達成目標下限」「保証目標値」→ ✅「考慮して」「達成すべき下限値」「目標値」
- 直訳を使わず、業界で定着した日本語訳を使う。❌「硬化させる」（hardening）「直列依存として乗る」→ ✅「セキュリティ強化」「リクエストパスに直列で含まれる」
- 主語と動詞を整合させる。❌「fail-secure に倒れる」→ ✅「fail-secure で拒否される」。「倒す」は能動行為の動詞なので、受動的な状況には使わない
- 定着したカタカナ語を漢語に無理に置換しない。❌「中核」← ✅「コア」
- 代名詞的な番号だけの呼び方を使わない。❌ L1/L2/P1。選択肢には役割が伝わる名前を付ける。先行文書の「案 A」等を引用するときはリンクを添える
- 一度定義した用語に、同義の言い換えや単位を毎回重ねない。「更新間隔」と決めたら「N 分間隔」「更新確認間隔 N 分」に散らさない
- ドメインの概念は、エンティティとして名前を付け、識別子・ライフサイクル・不変条件を伴う存在として書く。❌「〜という型」「観測された値」として記述する。型や値として書くと、ドメインの制約がドキュメントにも設計にも現れない。詳細は `kamae` スキル

## 中身のない表現

禁止語はコードスパンで囲んでいます。引用であることを示すためと、textlint の検査対象から外すためです。

- 予告と総括: `重要なのは〜である` `本書では〜を扱う` `まとめると` `〜に他ならない`
- 空虚な形容: `不可欠` `核心的` `鍵となる` `多角的` `包括的`
- 空虚な動詞: `掘り下げる`
- 中身のない強調: `大いに`
- 比喩・暗喩: `設計の天井` `成功の鍵` `銀の弾丸` `羅針盤` `ボトルネックの根` など、対象を別物に見立てる表現。何を指しているかを直接書く。✅「AWS インフラ起因のダウンタイムだけを反映した値」「最も影響の大きい要因」「判断基準」

## 主張と根拠

指摘・主張には具体的な根拠を添えます。根拠がない指摘はしません。

- 因果を主張するときは、その機構を一文で示す
- 区別すべき対象を一括りにしない
- 複数要因を単一原因に還元しない
- 否定・限定するときは、否定する命題を正確に書く
- 検出・保証・解決を「必ず」できるかのように書かない
- 根拠のない緩和で主張の強度をぼかさない。❌「〜と言えるだろう」。推量・仮定を表す場合は残す

## 自動検査

語彙のうち判定が一意に決まるものは自動化しています。検査語彙の正本は `~/.claude/textlint-rules/no-prohibited-expression.js` です。

- 外部サービスへ送る本文は、送信の直前に `~/.claude/hooks/lint-outgoing-body.ts` が textlint にかけます。対象は `gh pr create` / `gh pr edit`、`confluence create` / `confluence edit`、`jira create` / `jira edit`、`jira comment add` です。手で確認する必要はありません
- ファイルとして残す長文は `doc-style-checker` サブエージェントに委譲します。このエージェントは Bash を持たないため textlint を実行できず、`~/.claude/agents/doc-style-checker.md` に写した同じ語彙を Grep で見ます。語彙を変えるときは正本とこのエージェント定義の両方を直します
