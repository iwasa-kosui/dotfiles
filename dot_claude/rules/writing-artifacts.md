# 成果物テキスト: 4つの観点

`communication-style.md` の言葉遣いのルールに加えて、ファイルとして残す文書ではこの4観点で見ます。観点はこれ以上増やしません。新しい失敗パターンが見つかったら、該当する観点の下に例として足してください。禁止事項を並列に足し続けると、どこを見ればよいか分からない一覧になります。

- 事実は検証されているか
- 主張と根拠はつながっているか
- 読み手の手間を増やしていないか
- 構成は文書種別の型に従っているか

主張と根拠のルールは `communication-style.md` にあります。

## 事実は検証されているか

推測・アナロジー・「よくある命名パターン」を根拠に書いた記述は、読み手がそのとおりに動いて失敗します。

### 固有名

CLI サブコマンド・API エンドポイント・識別子は、実在を確認してから書きます。社内ツールのコマンド名、内部 API パス、フィールド名、テーブル名、環境変数名が対象です。命名パターンからの類推で書いてはいけません。CLI やドメイン固有ツールほど、命名の一貫性は保証されません。

- ❌ 既存文書の `foo user` `foo organization` から `foo device` の存在を類推する
- ✅ `--help` で確認する。リポジトリ内を検索して用例を確認する。用例が1件もないものは存在しない可能性が高い
- 確認できないものは `[要確認]` のプレースホルダにする。捏造した具体名より TODO のほうが読み手を欺かない
- 実在を確認できないコマンドを含む手順は `> [!NOTE]` で明示し、誰がいつまでに確定するかを書く

### 時間で無効になる記述

月や日付に言及するときは、必ず西暦を添えて絶対日付にします。文書は数ヶ月から数年後に参照されるため、執筆時点に依存する相対表記だと、翌年以降の読者は何年の話か判断できません。

- ✅ `2026-08-14`、`2026年10月`、`2026年8月末`。期間なら `2026-08-06 〜 2026-08-20`
- ❌ `10月から`、`8月末リリース`、`来月`、`今四半期`、`先スプリント`
- Jira 課題の description や Slack のやりとりを転記するときは、口語の相対表記が混入しやすい。執筆日を基準に絶対化する
- 実施時点や実行時点が基準になる表現は、相対表記のままでよい。Runbook の「N 日待つ」「N 分後」、バリデーション条件の「本日より過去であること」、顧客の発言の引用が該当する
- 「今日」「本日」「昨日」「明日」は自動検査の対象外にしている。上記の実行時点基準の用法が多数を占め、機械的に区別できないため。執筆時点を指しているものは読み直しで拾う
- PR 番号・スプリントのテーマ ID など揮発する識別子を本文に直接書かない。マージ済みのドキュメントへリンクする

### 対策と問題の対応

- 対策を並べるときは、問題の発生経路を先に特定し、各対策がどの経路のどの層に効くかを対応付ける。効き先が違う対策を「多段防御」の名目で並べない
- 対策ごとに、それが防ぐ失敗シナリオを1つ示せることを条件にする。示せないものは載せない

## 読み手の手間を増やしていないか

### 表と図

- 選択肢の比較・論点の整理・Pros/Cons を表形式にしない。見出しと箇条書きで書く
- 表は、セルの大半が短い定型値のときだけ使う。型名、制約、カラム名、環境変数名などが該当する
- Mermaid 図の内部識別子を本文・見出し・箇条書きから参照しない。gantt の task ID、sequenceDiagram の participant 名が対象。人間はプレビューで図を見るため、内部識別子はテキストとして見えない。概念名・役割名で書く

### 列挙

- 直後に列挙する対象を、抽象カウントや掛け算で数えない。❌「3 バケット × 3 オブジェクト」→ ✅「以下の3つのバケット」と書いて箇条書きにする
- 列挙済みの対象を再度数え直さない。❌「上記 3 オブジェクトを…」→ ✅「上記の各オブジェクトを…」

### 書かないこと

読者が自力で補える、または文書種別から自明なことは書きません。

- 実装時に別ドキュメントへ落とす旨。「Runbook 化する」「実装フェーズで公開 IF に記載」など
- セクション見出しと同じ内容の導入文
- 同じ主張の言い換え・要約の繰り返し
- 接続や評価のためだけの文。「それ自体はよいことである」
- 読者との問答形式の修辞。問いを立てて一語で答える
- コードが既に語っていることのコメント。`getUser()` の直前に「ユーザーを取得する」と書かない。自明でない why だけを書く。なぜこの実装を選んだか、なぜこの順序でなければならないか、なぜ一見冗長な処理が必要か
- 分量は絞ります。Confluence のコメントやスタンドアップ投稿は70行以内を目安にし、公開前に削ります。長いほど読まれません

## 構成は文書種別の型に従っているか

### 章立て

- 範囲の章には、扱うこと・扱わないこと・対象の境界だけを書く。スコープや背景の前提が該当する。実現方式の説明や選択肢の比較は載せない
- 選択肢の提示 → 比較 → 決定 の順を守る。決定前に結論だけ先出ししない
- 背景・前提には、なぜ必要か・制約・所与の条件を書く。各選択肢の中身は選択肢の章に書く
- 確定済みの上位ドキュメントの内容を再説明しない。参照リンクと、その文書で新たに決める点に分量を集中する
- 章番号による予告や見出しの言い換えを書かない。❌「6 章で整理する」「〜を当てはめた結果です」
- コミットメッセージにはトリガーを書かない。❌「レビュー対応」「フィードバック反映」「指摘を修正」。変更内容と理由を自己完結的に書く。詳細は `pr` スキル

### 参照

- 関連文書は本文の該当箇所からインラインリンクする
- 末尾に参考資料の一覧だけを置くセクションは作らない
- コード・設定の根拠は、可能ならリポジトリ内パスまたは恒久 URL にリンクする
- Jira 課題は URL でリンクする。❌ 裸の課題 ID を書く。ID だけでは開けず、読者が検索する手間が発生する

## 自動検査で拾えないもの

`ADVISORY_CHECKS` は誤検知が避けられないため hook では有効にしていません。英語の括弧書き、だ・である調、裸の Jira 課題 ID が該当します。固有名詞の併記、箇条書き内の言い切り、`UTF-8` のような規格名を機械的に区別できないためです。

自動検査で拾えないものは、4観点に沿った読み直しで見ます。括弧書きの多用、見出しの言い換え、体言止めの地の文、表の乱用、主張と根拠のつながり、事実の裏取りが対象です。
