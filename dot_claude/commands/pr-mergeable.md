## Your task

You MUST use Japanese.

PR を診断し、マージ可能にするための完了条件プロンプトを組み立てて `/goal` セッションとして起動します。
診断は `pr-autofix` の収集スクリプトに任せ、あなたはブロッカーから受入条件への変換とユーザー対話に専念してください。

## フロー

### ステップ1: 診断

```bash
bun ~/.claude/skills/pr-autofix/scripts/collect.ts $ARGUMENTS
```

引数に PR 番号か URL があればそれを、なければ現在ブランチの PR を対象にします。PR が見つからずコマンドが失敗した場合は、その旨を報告して終了します。

標準出力に PR の基本情報、CI 失敗ジョブとエラー行、active なレビュースレッドの要約が出ます。JSON 全文は読みません。「エラー行を抽出できず」と出た失敗ジョブがあれば、そのジョブだけ `gh-collector` に `<workspace>/ci-failures.json` の該当 `log_excerpt` を読ませ、エラー本文と `file:line` を要約させます。

### ステップ2: ブロッカー判定

次の4つを見ます。

- CI 失敗ジョブ
- active なレビュースレッド。`resolved` でも `outdated` でもないもの
- `mergeable: CONFLICTING`
- `draft: true`

いずれもなければ「このPRはマージ可能な状態です」と報告して終了します。1つ以上あればステップ3へ進みます。

### ステップ3: プロンプト本文の組み立て

Write ツールで `/tmp/pr-mergeable-body.md` に次の形で書きます。`### 前提条件（常に必須）` は起動スクリプトが付けるので書きません。

```
PR #<番号> (<タイトル>) をマージ可能な状態にする

## 現状の問題

- <ブロッカーの箇条書き。CI 失敗には抽出したエラー行、レビュー指摘には file:line と要約を添える>

## 完了条件

以下の**すべて**が満たされた時点で完了とする。

### 受入条件
- <ブロッカーごとに生成した条件>

### PR対応時の前提条件（active なレビュースレッドがある場合のみ含める）
- PRの全レビューコメントについて対応要否が判定されていること
- 対応が必要なコメントには修正コミットのハッシュ付きで返信されていること

### セルフレビュー前提条件（PRがdraft状態の場合のみ含める）
- `/review` でセルフレビューを実行し、指摘事項があればすべて修正すること
- セルフレビュー完了後、`gh pr ready` で Ready for review にすること
```

受入条件の生成ルール:

- CI 失敗: 「GitHub Actions の CI ジョブ `<失敗ジョブ名>` が通過していること」。抽出したエラー行は「現状の問題」に載せる
- active なレビュースレッド: スレッドごとに「`<file>:<line>` の指摘（<要約>）に対応すること」
- コンフリクト: 「ベースブランチ (`<base>`) とのマージコンフリクトが解消されていること」
- draft: 受入条件には入れず、セルフレビュー前提条件セクションで扱う

### ステップ4: プレビューと起動

```bash
~/.claude/scripts/goal-session.sh --dry-run /tmp/pr-mergeable-body.md
```

出力されたプロンプト全文をユーザーに示し、次のように確認します。

> 以下のプロンプトで `/goal` セッションを起動します。修正点があれば教えてください。

修正があれば body を書き直して再度プレビューします。承認を得たら `--dry-run` を外して起動します。

```bash
~/.claude/scripts/goal-session.sh /tmp/pr-mergeable-body.md "PR #<番号> をマージ可能にする"
```

起動したワークスペース名をユーザーに伝えます。

## 重要なルール

- 診断はスクリプトとサブエージェントに任せ、司令塔のトークン消費を最小化する
- 受入条件はチェッカーモデルが**機械的に判定できる**形で書く
- 常に必須の前提条件は `goal-session.sh` が付ける。ユーザーが削除を希望した場合は、リモートの CI 状態を確認せずに完了と判定される危険を説明して残すことを推奨する
- プロンプトは簡潔に。冗長な説明はチェッカーモデルの判定精度を下げる
- 「現状の問題」には、起動先のセッションが着手しやすいよう、エラー行やコメント要約などの参考情報を含める
