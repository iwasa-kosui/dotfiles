## Your task

You MUST use Japanese.

`/goal` に渡す完了条件プロンプトをユーザーと対話的に組み立て、`/goal` セッションとして起動します。
調査はサブエージェントに委譲し、あなたはヒアリングとプロンプト組み立てに専念してください。

PR をマージ可能にする目的なら、このコマンドではなく `/pr-mergeable` を使います。診断とブロッカーからの受入条件生成がそちらに入っています。

## フロー

### ステップ1: コンテキスト収集（サブエージェントに委譲）

Agent ツールで `subagent_type`: `Explore` のサブエージェントを起動し、既存の spec / plan / design doc からの受入条件抽出を委譲する。

```
サブエージェントへのプロンプト:

以下のパスで spec / plan ファイルを探し、受入条件・完了条件・成功基準に相当する記述を抽出してください。

検索パス:
- docs/superpowers/specs/*.md
- docs/**/*-design.md
- docs/**/*-plan.md
- プロジェクトルート直下の *.plan.md

## 出力形式

ファイルが見つかった場合:
- ファイルパス
- 抽出した受入条件・完了条件のリスト

見つからなかった場合:
「該当ファイルなし」とだけ返す
```

- `$ARGUMENTS` が指定されている場合は、サブエージェントの結果を待たずにステップ2に進んでよい（`$ARGUMENTS` をタスク概要の初期入力として扱う）

### ステップ2: タスクと受入条件の確定

ユーザーに以下を確認する（spec から抽出できた項目はスキップ可能）:

1. **何を達成したいか**（タスクの概要）
2. **受入条件**（チェッカーモデルが機械的に判定できる、測定可能な条件を定義する）
   - 良い条件の例: 「`npm test` が exit 0 で終了する」「`src/auth/` 配下に新しいミドルウェアファイルが存在する」
   - 悪い条件の例: 「コードがきれいである」「設計が良い」（主観的で検証不能）
3. **制約・注意事項**（あれば）

AskUserQuestion を使って効率的に確認する。一度に大量の質問をせず、文脈に応じて段階的に聞く。

### ステップ3: プロンプト本文の組み立て

Write ツールで `/tmp/goal-builder-body.md` に次の形で書く。`### 前提条件（常に必須）` は起動スクリプトが付けるので書かない。

```
<タスクの概要>

## 完了条件

以下の**すべて**が満たされた時点で完了とする。

### 受入条件
- <ユーザー定義の条件1>
- <ユーザー定義の条件2>

### PR対応時の前提条件（PRレビュー対応タスクの場合のみ含める）
- PRの全レビューコメントについて対応要否が判定されていること
- 対応が必要なコメントには修正コミットのハッシュ付きで返信されていること
```

### ステップ4: プレビューと起動

```bash
~/.claude/scripts/goal-session.sh --dry-run /tmp/goal-builder-body.md
```

出力されたプロンプト全文をユーザーに示し、次のように確認する。

> 以下のプロンプトで `/goal` セッションを起動します。修正点があれば教えてください。

修正があれば body を書き直して再度プレビューする。承認を得たら `--dry-run` を外して起動する。

```bash
~/.claude/scripts/goal-session.sh /tmp/goal-builder-body.md "<タスク概要>"
```

起動したワークスペース名をユーザーに伝える。

## 重要なルール

- 調査はサブエージェントに委譲し、司令塔のトークン消費を最小化する
- 受入条件はチェッカーモデルが**機械的に判定できる**形で記述する。主観的・曖昧な条件は具体化するようユーザーに促す
- 常に必須の前提条件は `goal-session.sh` が付ける。ユーザーが削除を希望した場合は、リモートの CI 状態を確認せずに完了と判定される危険を説明して残すことを推奨する
- プロンプトは簡潔に。冗長な説明はチェッカーモデルの判定精度を下げる
