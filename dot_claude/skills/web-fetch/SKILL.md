# Web Fetch

## いつ使うか

URL の内容を読む必要があるとき。外部の公開ドキュメント、仕様、リファレンスを参照するとき。

WebFetch ツールを呼びそうになったときは、必ず先にこのスキルを検討します。WebFetch は組織のポリシーで確認プロンプトが強制されており、呼ぶたびにユーザーの操作を要求します。加えて取得内容を小型モデルで要約して返すため、仕様を正確に読む用途では入力が劣化します。

### 使わない場面

- GitHub 上のリソース。PR、Issue、リポジトリのファイル、Actions のログは `gh` CLI を使う。認証付きで取得でき、非公開リソースも読める
- Jira 課題と Confluence ページ。`atlassian-collector` サブエージェントに委譲する
- 検索して情報源を探す段階。WebSearch を使う。URL が確定してからこのスキルに来る

## 設計思想

取得先をコマンド側の allowlist で制限し、コマンド単位の許可だけで運用します。ドメインごとの権限設定を増やさずに済みます。

出力は要約しません。原文を Markdown に変換して全文返します。要約は非可逆で、仕様の細部を落とすためです。

## 手順

### 1. 取得する

```bash
web-fetch <url>
```

標準出力に Markdown、標準エラーに拒否理由が出ます。

### 2. 終了コードで分岐する

| 終了コード | 意味 | 対処 |
|---|---|---|
| 0 | 成功 | 出力を読む |
| 1 | 取得失敗または HTTP エラー | URL を疑う。allowlist の問題ではない。タイポとリンク切れを確認する |
| 2 | 許可判定で拒否 | 手順3へ |
| 3 | 引数不正 | 引数は URL 1つだけ |

### 3. 許可外ドメインだったとき

拒否されると、許可されているドメインの一覧が標準エラーに出ます。

**allowlist を勝手に書き換えないこと。** 取得先を増やす判断はユーザーのものなので、ドメイン名を示して追加してよいか確認します。

追加してよいと言われたら、2箇所を直します。

1. chezmoi のソース `dot_config/web-fetch/allowlist` に1行足す
2. `chezmoi apply` で配置先に反映する

配置先のファイルだけを編集しても `chezmoi apply` で上書きされて消えます。ソースを直します。

記法は1行1ドメイン。`#` 始まりはコメントです。先頭に `.` を付けると、そのドメインとサブドメインの両方に一致します。

### 4. 長いページを読むとき

このコマンドは要約しないため、出力がそのまま文脈に載ります。長いページをそのまま読むとコンテキストを大きく消費します。

知りたいことが限定的な場合は、ファイルに落としてから読み取りを委譲します。

```bash
web-fetch <url> > /tmp/fetched.md
```

そのうえで `doc-reader` サブエージェントに `/tmp/fetched.md` を読ませ、必要な箇所だけを返させます。全文はサブエージェントの文脈で消えます。

## 注意点

- HTML 以外はそのまま返ります。JSON やプレーンテキスト、`.md` を返すエンドポイントは変換されません
- HTML の場合は本文だけが変換されます。`nav` `header` `footer` `aside` `script` は落ちるので、ナビゲーションの文言は出力に含まれません
- リダイレクトはホップごとに許可判定をやり直します。許可ドメインから許可外へ転送されるページは、転送先が拒否されて終了コード 2 になります
- このスキルは呼び出されたときにしか読み込まれません。WebFetch を呼ぶ前に思い出す保証がないので、URL を扱う作業かどうかを取得の前に確認します
