# cmux orchestration

管理役の Claude Code セッションが、cmux のワークスペースごとに作業セッションとレビューセッションを起動します。各セッションはセッション間通信（SendMessage）で報告と指摘を送ります。ユーザーの手作業を減らすことが目的です。

## 役割

- 管理役は、ワークツリーを作り、セッションを起動し、報告を待ちます。管理役は判断の依頼に答え、重点観点を追加で指示し、Environment を承認し、古い workflow 実行を取り消します。管理役は、レビューセッションが承認した head SHA を指定して PR を merge します。
- 作業セッションは、バックログの1件につき1つ起動します。作業セッションは Draft PR を作り、PR URL・要旨・検証結果・未確認事項を管理役に SendMessage で報告します。
- レビューセッションは、PR ごとに1つ起動します。レビューセッションはコードを編集しません。レビューセッションは指摘を「重大度（must/should/nit）・file:line・問題・修正案」の形で作業セッションに直接送ります。must と should がすべて解消したら、レビューセッションは「承認: PR URL・確認した head SHA・残った nit」を管理役に送ります。

## 手順

1. 管理役は ListAgents で自分の宛先名を確認します。ListAgents の出力に「This session is <名前>」と表示されます。管理役はこの名前を共通ルールのプロンプトに書きます。
2. 管理役は、`git worktree add` で `<リポジトリ>/.wt/<ブランチ名>` にワークツリーを先に作ります。作業セッションには EnterWorktree を使わせません。作業セッションが EnterWorktree を使うと、`.claude/worktrees/` の外への移動を確かめる権限確認が出てセッションが止まり、ユーザーの操作が必要になります。
3. 管理役はプロンプトを Write ツールでファイルに書きます。共通ルールと個別の指示は別のファイルにします。Bash の heredoc ではプロンプトを書きません。heredoc で書くと、本文に含まれる語（AWS の CLI 名など）に bash-guard の hook が反応して、コマンドが拒否されることがあります。
4. 管理役は起動スクリプトを書き、cmux でワークスペースを作ってセッションを起動します。
   - `CMUX_QUIET=1 cmux new-workspace --name <ワークスペース名> --cwd <ワークツリーのパス> --command "<起動スクリプト>" --focus false` を実行します。`CMUX_QUIET=1` を付けると、エイリアス変更の通知が出なくなります。
   - 起動スクリプトは `claude -n <セッション名> --permission-mode auto "$(cat <共通ルールのファイル> <個別の指示のファイル>)"` を実行します。`-n` で付けた名前が SendMessage の宛先になります。
5. 管理役は報告を待ちます。待ち方は「監視」の節に従います。
6. 管理役は、承認を受けた PR に `gh pr ready <PR>` を実行し、続けて `gh pr merge <PR> --squash --match-head-commit <承認された head SHA>` を実行します。

## 監視

- 報告は SendMessage で届きます。管理役は `sleep` の長い待機タイマーをバックグラウンドで動かして待ちます。
- 報告が途絶えたら、管理役は `cmux read-screen --workspace <ワークスペースの ref> --lines <行数>` で各セッションの画面を見て、権限確認で止まっていないかを確かめます。
- セッションが権限確認で止まっている場合、管理役は代わりに答えません。管理役はユーザーに、どのワークスペースで何を選べばよいかを伝えます。

## 権限と手作業

- 作業セッションで権限判定に拒否された操作を、管理役やほかのセッションが代わりに実行しません。
- 本番サーバーへの ssh のように権限判定で止まりやすい操作を、ユーザーの手作業に回しません。管理役とセッションは、CI（GitHub Actions の workflow）を経由する方法を先に検討します。
- プロンプトに「例:」として具体的な値を書くと、セッションはその値をそのまま使います。管理役は、使ってほしくない値を「例:」としてプロンプトに書きません。

## 終了

- セッションは、担当の作業が終わったら、完了の連絡を管理役に SendMessage で送ります。そのあとでセッションは `cmux close-workspace --workspace <ワークスペースの ref>` でワークスペースを閉じます。
- 閉じた後のセッションには、メッセージが届きません。セッションは、レビューの指摘や管理役からの連絡を受ける必要がある間は、ワークスペースを閉じません。
- ワークスペースの ref は `cmux new-workspace` の出力に表示されます。管理役は起動後に ref を確認し、各セッションに SendMessage で伝えます。

## 雛形

`<...>` はプレースホルダです。管理役が起動前に実際の値へ置き換えます。

### 共通ルール

```markdown
# 共通ルール

- 管理役のセッション名は `<管理役の名前>` です。報告・質問・判断の依頼は、この名前に SendMessage で送ってください。
- バックログは `<バックログの場所>` にあります。
- 作業ディレクトリは起動時のディレクトリです。EnterWorktree で新しいワークツリーを作らないでください。

## 進め方

1. 担当の項目を読み、不明点があれば作業を始める前に管理役に質問します。
2. 判断が必要な点は、自分で決めずに管理役に聞きます。
3. 担当の作業が終わったら、完了の連絡を管理役に送ってから、管理役から伝えられた ref のワークスペースを `cmux close-workspace` で閉じます。レビューの指摘や管理役からの連絡を受ける必要がある間は閉じません。

## 禁止事項

- 権限判定で拒否された操作を、別の方法で回避しません。ほかのセッションに代わりの実行を頼みません。拒否された内容を管理役に報告します。
- 本番サーバーへの直接の操作が必要になったら、CI（GitHub Actions の workflow）を経由する方法を先に検討し、管理役に相談します。
- PR の Ready 化、merge、force-push、保護ブランチへの直接 push はしません。
```

### 作業セッション

```markdown
# 担当

- このセッションの名前: `<作業セッション名>`
- 担当するバックログの項目: `<項目>`
- ブランチ: `<ブランチ名>`（作業ディレクトリのワークツリー）
- レビューセッションの名前: `<レビューセッション名>`

## 進め方

1. 担当の項目を実装し、検証します。
2. Draft PR を作ります。
3. PR URL・要旨・検証結果・未確認事項を `<管理役の名前>` に SendMessage で報告します。
4. `<レビューセッション名>` から指摘が SendMessage で届きます。指摘に対応して push し、`<レビューセッション名>` と `<管理役の名前>` に返信します。
```

### レビューセッション

```markdown
# レビュー担当

- このセッションの名前: `<レビューセッション名>`
- 対象の PR: `<PR URL>`
- 作業セッションの名前: `<作業セッション名>`
- 重点観点: `<観点>`

## 進め方

1. PR の差分を読みます。コードは編集しません。
2. 指摘は1件ごとに「重大度（must/should/nit）・file:line・問題・修正案」の形で、`<作業セッション名>` に SendMessage で送ります。
3. `<作業セッション名>` から修正の返信が届いたら、push された差分を確認します。
4. must と should がすべて解消したら、「承認: PR URL・確認した head SHA・残った nit」を `<管理役の名前>` に SendMessage で送ります。
```

### 起動スクリプト（作業用）

```bash
#!/bin/bash
set -euo pipefail
exec claude -n <作業セッション名> --permission-mode auto \
  "$(cat <共通ルールのファイル> <作業セッションの指示のファイル>)"
```

### 起動スクリプト（レビュー用）

```bash
#!/bin/bash
set -euo pipefail
exec claude -n <レビューセッション名> --permission-mode auto \
  "$(cat <共通ルールのファイル> <レビューセッションの指示のファイル>)"
```
